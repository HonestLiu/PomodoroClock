# 生活成长游戏与主动 AI：产品及实施提案

状态：产品路线提案 v3，2026-11-01。第一期已实现并通过规则、SQLite 和浏览器流程验证，实际实现范围及规则见 [任务看板模块](05-modules/quests.md)；本文的第二至第四期及部分实体设计仍是规划，不代表已具备。

## 1. 产品定位

用户提供现实中的目标，AI 担任规划师、每日任务发布者和陪伴者，把长期愿望变成今天能完成的小行动。完成现实行动推动角色和目标共同成长。

产品的主要循环：

提出目标 → 生成内部任务链 → 看板发布当前可接任务 → 用户接取 → 临时进入当天待办 → 当天完成后正式归档并结算；未接取或未完成则排后续日期重发。

番茄钟是任务执行工具；聊天是与伙伴交流的入口；今日任务与目标进展成为产品中心。游戏反馈应服务于现实进展。

第一版暂以“现实目标成长＋轻量冒险包装”为设计假设。角色、地图、剧情的表现程度待用户选择，不阻碍先做核心循环。

## 2. 当前代码基础及缺口

已核对源码：
- `src/stores/aiChatStore.ts`：自然语言建任务、任务拆解、每日计划、日报/周报；建任务和拆解可采纳，每日计划与报告只读展示。会话保存在运行时 store，不能承担长期目标记忆。
- `src/lib/ai/`：模型适配、结构化输出、时间上下文、估时校准、规则装箱等基础可复用。
- `src/lib/growth.ts`：金币和经验由累计专注秒数派生，已有商店、等级奖励和会员基金。
- `src/stores/growthStore.ts`：本地账本串行写入，写库成功后发布状态；已有归档去重。
- 任务、日历、专注记录、系统通知、SQLite/IndexedDB 双运行时可复用。

主要缺口：长期目标实体、独立任务看板、隐藏前置依赖、接取批次与临时待办、跨日收回和重发、完成后归档、暂存专注记录、持久化记忆与主动调度。

旧 AI 文档要求“用户逐次确认才落库”。新方向需要在实现时明确更新为“AI 在授权范围内自动发布到看板，用户自行接取后才进入当天待办；超出范围才确认”；本文尚不修改现有行为。

## 3. 玩家的体验

### 第一次：创建一条主线

用户：“我想三个月内具备独立开发 ESP32 小项目的能力，每天约 40 分钟。”

伙伴先确认当前基础、可用设备、每周投入、完成标准。已明确的信息不重复问；可先提出一个可编辑的初始路线。

路线示例：
1. 点亮开发板，能独立编译和烧录。
2. 完成按键、传感器和显示交互。
3. 完成一个可演示的小项目，并能解释主要设计。

每个阶段都有可判断的成果标准。确认路线后才启用每日自动发布；默认一条主线，可加一条小习惯。用户可暂停、修改和归档。

### 独立的任务看板

看板是专门的接任务页面，展示当前已经发布且满足前置条件的全部任务。看板任务、普通 ToDo 任务各有独立生命周期。

每张卡展示标题、可理解的任务说明、完成标准、预计投入、固定奖励与“接取”按钮。可以说明来自哪个目标，但不显示未解锁的任务名称、整条任务树、后续步骤或“还有 N 个隐藏任务”等剧透信息。

用户可接可不接。不接不会自动进入待办；该任务回到后续日程，未来再次发布。只要目标仍在推进，必要步骤就持续保留，不能因为多次没接而永久丢弃或跳过。允许通过暂停/修改目标改变路线，不强制某天接取。

默认发布量和接取建议考虑当天时间预算；“显示所有可接任务”指当前已发布的可接集合，不包括未来排程和未解锁任务。

### 前置与后置：后台规划，逐步显现

内部例子：编译烧录 → 点亮 LED → 按键控制 LED。用户先只看见“编译烧录”。完成且归档后，系统才允许后置任务在下一次发布时出现。未完成、仅接取、仅计时到点都不能解锁。

支持一个前置解锁多个后续，也支持多个必要前置全部完成后才能解锁。依赖由确定性规则校验，无环、不能引用未知任务；模型不能绕过前置条件。后置任务的标题和说明也不得通过通知、聊天或任务搜索提前泄露。

### 接取：只进入当天待办

用户点“接取”后：
1. 看板该卡标记为“已接取”，禁用重复接取。
2. 创建这一天的接取记录，在“今天”的 ToDoList 展示临时待办，可绑定番茄钟。
3. 普通任务总览、普通清单、未来计划和任务总数均不纳入这项未完成的临时任务。

临时待办使用与普通待办一致的勾选和专注交互，但有明确的“看板任务·今日有效”来源标记。第一版直接勾选即表示用户确认完成标准，不强加额外成果表单。用户愿意时可以附备注。

### 当天完成：正式归档

勾选完成时，一次性完成：确认本次接取仍有效 → 正式完成该游戏任务 → 在普通任务总览建立已完成任务档案 → 转入符合口径的专注记录 → 发放奖励 → 更新目标成果 → 解锁后续资格。

任务与关联专注记录同时进入正式统计，任务当天完成时间决定任务完成日，专注记录保留实际起止时间。不计时也允许完成，专注时长为零。不能用番茄钟结束替代勾选完成。

正式任务沿用现有总览的“已完成”分区/开关可查看；首页总数和报表按统一口径计算。看板可在当日保留“已完成”反馈，历史不堆在可接列表中。

### 当天未完成：收回，再择日发布

当天未勾选的临时待办在日界线失效，从今天 ToDoList 消失，不滚成普通逾期任务。看板任务保留，以“待重新发布”状态进入后续排程；下次再次发布时重新显示“接取”，不能沿用上次的已接取状态。

未接取的发布项也进入后续排程。未接取和接取后未完成分别记载，供 AI 调整安排，但都不作为普通未完成任务计数。任务不会因本次发布失效而被永久删除。

第一版建议按固定的玩家本地日历日到 00:00 结算。应用关闭期间未发生界面操作，重启时先收回过期接取，再显示今天，不补出过去多天的待办。

### 专注时间的暂存与结算口径

用户要求“完成才计入，没完成不计入”：
- 本次接取上的专注先写到游戏内部的暂存记录，计时器可显示当次计时，但普通任务总览、专注记录页、报表、热力图、桌面组件和成长结算都不能提前纳入。
- 当天完成时，才把允许计入的暂存记录与已完成任务一起转为正式记录。
- 当天未完成时，不发奖励、不写普通任务档案、不写正式专注统计；内部保留必要尝试信息以支持重发与防重。
- **当前实施规则（用户已同意沿用）**：周一失败接取投入 20 分钟，周三重新接取并投入 30 分钟后完成，最终计入 30 分钟。若用户选择累计投入，则改为完成时一次性计入 50 分钟，但未完成前仍不进入正式统计。
- 普通手动任务的记录和奖励规则保持原样，这一延迟结算规则只针对看板任务。

## 4. 状态、主动性与调度边界

任务本体与接取尝试分开建模：任务本体承载目标与依赖，一项任务可有多次发布和接取尝试，最终只完成及结算一次。

| 状态 | 看板/今日待办 | 普通任务总览与统计 |
| --- | --- | --- |
| 前置未满足 | 不展示 | 不纳入 |
| 待发布 | 不在本期可接列表 | 不纳入 |
| 已发布、未接取 | 看板可接 | 不纳入 |
| 当日已接取 | 看板标“已接取”；今日临时待办可见 | 不纳入 |
| 当日已完成 | 看板反馈完成；今日可查看完成项 | 正式归档任务及合规专注记录，结算奖励 |
| 过期未完成 | 从今日待办移除，回后续排程 | 不纳入 |

| 触发 | AI/系统自动动作 | 约束 |
| --- | --- | --- |
| 新一天启动/运行中跨日/唤醒 | 收回过期临时待办，再发布符合条件的任务 | 先收回后展示，不重复发布、不补出过期列表 |
| 任务未接取 | 排后续日期再发布 | 必要步骤持续保留，不能饿死在队尾 |
| 接取后未完成 | 收回本次尝试，择日重发 | 后续仍锁定，不进入普通任务总览 |
| 用户完成任务 | 正式归档、结算、解锁依赖 | 同一任务一次有效完成、一次奖励 |
| 用户反馈太难/时间不足 | 调整未来任务粒度及排程 | 不擅自改动已接取任务的标准和奖励 |
| 每周复盘 | 依据完成/跳过/失效尝试建议路线调整 | 用户选择不接不等于能力不足 |

重发按预计耗时、目标优先级、等待时间和近期尝试安排。第一版每天同一任务至多发布一次；失败后不在当天反复推送。临近目标期限仍不强制接取，可以提示需要调整路线或日期。

AI 自动发布到看板，不自动替用户接取；不能编辑普通手动任务。更改总目标、期限、投入上限、现实支出、奖励兑换和会员基金操作仍需用户决定。默认每日一次公告，额外通知遵守免打扰时间。

## 5. 规划与记忆

规划分三层：
- 长期：目标、成功标准、阶段路线；信息变化或周复盘时再修订。
- 近期：下一阶段可执行的任务池，明确依赖与完成标准。
- 今日：根据预算、截止约束、已接取任务和近期状态，选择小量可接取任务；用户决定是否接取。

使用现有 timebox 的确定性容量约束；AI 不能以叙事理由突破时长预算。先保留缓冲，再分配任务。目标依赖知识来源时允许用户提供课程大纲/资料，AI 不凭空编造课程章节和学习成果。

持久化记忆保存明确事实：偏好、可用时间、用户自评基础、近期完成成果、困难原因、路线版本。自动推断标记为待确认；用户可以查看、修改和删除。聊天仅引用相关摘要，不反复上传全量历史。

先采用简单可解释的调整规则，例如最近几次任务经常超时则减小单次任务；具体阈值在小样本试用后校准，不能把一次未完成判断成能力不足。

## 6. 成长及经济规则

保留既有专注金币/经验与兑换能力，不重置历史余额、等级或已领取奖励。

新增任务奖励与阶段奖励，必须先统一奖励账本：
- 来源区分 `focus_record`、`quest_completion`、`milestone_completion`。
- 每笔有稳定事件 ID、来源、规则版本、金额/经验、时间；同一事件最多结算一次。
- 任务发布时固定奖励，不让模型直接填写最终金币数。模型可建议任务种类，规则引擎按估时、类别、阶段等受控字段计算。
- 看板任务的专注奖励与成果奖励一律在任务成功归档时结算；失败尝试不提前发放。明确两者叠加政策、奖励上限及拆分任务的预算分配，避免无限拆任务刷奖。
- 撤销完成必须有冲正/再结算规则；重新勾选不重复发奖。已有余额已消费时不强行产生不可解释的负数，具体策略在奖励阶段定稿。
- 手动任务有合理的基础奖励，避免用户被迫只做 AI 任务；自定义任意任务不能自行填写无限奖励。
- 游戏金币不自动兑换现金，不自动移动会员基金，不变更既有币值；新增奖励投入流通前核算对现有兑换经济的影响。

第一版奖励以少量固定任务奖励与清晰成长反馈为主。皮肤、房间装饰、称号等消耗项在核心循环稳定后增加；不先做复杂装备、随机抽奖或资源生产体系。

## 7. 页面布局方向

- 任务看板：独立入口，展示本期所有可接任务、已接取标记和当日完成反馈。未解锁/待重发任务不占可接列表。
- 今日：普通今日待办＋已接取且尚未失效的游戏临时待办；完成的游戏任务来自正式归档，避免重复展示。
- 目标：主线及支线、阶段路线、真实成果、暂停和修改。
- 成长：角色等级、经验与金币、现有商店、未来装饰与称号。
- AI 伙伴：保持原来的建任务/拆解/计划/报告能力，增加目标讨论、解释安排、反馈困难；与今日和目标页面共享上下文。
- 任务、日历、报表、专注作为现有工具继续可达；先增加首页和目标，不在首版彻底重排所有导航。

未来世界地图可以映射已解锁的目标章节，不预览后置任务：每个章节由现实里程碑解锁。剧情以已完成的真实事件为素材，不能虚构用户已经达成的成果。先验证日循环，再选择美术风格。

## 8. 技术落地

建议新增领域实体（名称为提案）：
- `goals`：成功标准、状态、预算、优先级、自动权限。
- `milestones`：目标关联、依赖、验收标准、状态。
- `goal_plan_versions`：路线及修订原因、版本。
- `daily_plans`：本地日期、时区、状态、输入快照、计划版本。
- `quests`：独立游戏任务本体，目标/阶段、完成标准、预算、依赖和生命周期；未完成前不创建普通 tasks 行。
- `quest_dependencies`：前置/后置边；客户端可见集合只暴露已解锁任务。
- `quest_offers`：每次发布的日期、窗口、状态与下一次发布安排。
- `quest_attempts`：每次接取的独立 ID、接取日、失效时间、完成/过期状态；与最终任务本体区分。
- `quest_focus_sessions`：按接取尝试关联的暂存专注会话，含稳定来源 ID、有效秒数及是否已结算。
- `quest_archives`：quest_id 到正式 task_id 的唯一映射，仅完成后生成。
- `goal_events`：完成反馈、阶段成果和用户调整；作为复盘依据。
- `reward_events`：按来源去重的发放/冲正记录，兼容现有账本。
- `agent_runs`：触发、输入版本、生成/验证/发布/失败状态、重试及幂等键。
- `player_preferences`：用户确认的偏好及主动模式设置。

AI 层做理解、拆解、选择与说明；规则层管日期、预算、依赖、有效引用、发布、奖励和幂等。

发布流程：触发 → 读取数据快照 → 规则选候选 → 模型补全/排序 → schema 与预算校验 → 检查输入版本未过期 → 事务发布看板任务及计划 → 记录完成运行。失败不能留下半份计划或重复任务。

接取流程：校验发布窗口及前置 → 原子创建当日尝试/标记已接取 → 今日页合并临时待办。普通任务查询不加临时任务；今日页单独查询后合并，不能先创建普通任务再仅靠页面隐藏。

专注流程：计时器的绑定扩展为普通任务或接取尝试；看板任务不能走当前“归档专注即入正式记录并发奖励”的路径。普通记录聚合入口本来直接读取 records，仅过滤任务列表不足以实现统计隔离。

完成流程：有效尝试、quest 状态、正式 task 档案、专注转入、奖励和解锁事件必须在同一事务结算；双运行时都支持，不能依靠两个独立 store 的先后异步保存模拟事务。

跨日处理：按到期时间校验，不依赖定时器恰好运行。若跨日时仍绑定过期游戏任务，暂停/终止该次任务计时，把有效片段留在内部尝试，不自动转成普通无任务专注。完成和收回竞争时按事务及有效期限裁决，拒绝重复或过期结算。重接生成新 attempt_id，不能串入旧尝试记录。

游戏已完成任务的撤销不能直接沿用普通任务取消勾选：必须定义奖励冲正及后置任务处理。第一版建议对已归档的游戏任务不提供普通取消勾选入口，之后以独立的成果修正流程处理；此项是实施建议，尚未定稿。

并发和日期：按玩家本地日期/目标/计划用途唯一约束；多窗口共用持久化锁/运行记录。时区改变、恢复睡眠、午夜切换、系统时钟变化均有明确策略，不能仅靠内存计时器或按钮禁用去重。

离线/未配置模型：继续用已确认路线及已缓存任务池排程，规则模式保留预算及去重。任务池耗尽时明确提示补充规划，不伪称是新的 AI 规划。生成失败不影响手动任务和奖励结算。

运行边界：第一版在应用运行、启动或唤醒时执行；软件完全退出后不承诺每天自动调用模型。关闭期间只补生成今天的任务，不补发一串过期任务。真正关闭应用后的后台调度另立后续里程碑。

长期目标与奖励必须分别核对现有云同步边界。首版明确为本机权威；在有去重合并方案前不宣称支持多设备一致发奖。模型调用有每日次数预算、缓存、超时和取消，不在每次计时 tick 调用。

## 9. 分阶段实施及验收

### 第一期：可连续使用的目标日循环（最小可玩版本）

先把体验跑通：一条主线 → 确认目标与预算 → 后台生成有依赖的任务链 → 看板发布 → 用户接取 → 今日临时待办 → 当天完成后归档结算，或跨日收回重发。

包含：目标与隐藏任务链持久化、任务看板、接取与今日临时待办、跨日收回/重发、完成后才写普通任务及专注记录、固定奖励账本兼容、离线基础排程。AI 页面原能力继续可用。

验收：
1. 前置 A 未完成时，后置 B 在看板、搜索、通知和伙伴说明中均不可见；完成 A 才允许发布 B。
2. 当前发布的可接任务全部可在看板查看；未接取不进入今日待办，未来仍可重发。
3. 接取后看板标“已接取”，今日只出现一份；普通总览/清单/总数均无该未完成任务。
4. 当日未勾选，跨日或重启时自动收回；不出现普通逾期项，之后重新接取才回到今日。
5. 失败接取产生的暂存专注不会污染记录页、报表、热力图、组件或金币/经验。
6. 完成时普通任务和符合口径的专注同时归档；无计时的完成任务时长为零。
7. 重启、多窗口、双击、午夜竞争及模型重试不重复接取、归档、发奖或解锁。
8. 旧任务、普通专注记录、余额、等级、商店及会员基金兼容保留。
9. 断网仍可接取已发布任务、执行、结算和按缓存规则重发；关闭数天只恢复当前日。
10. 周一失败、周三完成的专注归属按最终选定口径验证，旧 attempt 不得误挂新任务。

### 第二期：伙伴开始理解用户

增加偏好记忆、困难反馈、任务细分、周复盘、保底任务、少量有依据的主动提醒。调节策略先规则化，再考虑模型参与。

验收：用户说“今天只有 15 分钟”后仅调整可编辑任务；手动和已开始任务不被覆盖；新预算无法容纳时明确显示冲突。连续未完成后任务不会堆积，且能解释为何调整。

### 第三期：形成游戏的表达

选择角色和美术方向，加入目标章节、成长动画、称号、装饰、阶段挑战与伙伴对话。探索地图与现实阶段进展对应。

验收：真实成果可追溯，奖励反馈不打断工作，关闭动画后完整可用；游戏外观没有显著增加完成一项真实行动的步骤。

### 第四期：持续运行与更多生活领域

再考虑多目标资源分配、应用关闭后的后台计划、移动端、可靠的多设备账本、更多领域的目标模板和资料接入。依前三期使用反馈决定优先级。

## 10. 待用户逐步确定的选择

不需要一次决定所有细节，先确认这三项即可推进第一期规格：
1. 游戏表现：现实成长的轻包装，还是剧情/角色/世界探索优先？
2. 首个试用目标：选择一个真实目标，方便用一周验证任务是否有帮助。
3. 伙伴性格：温和陪伴、清晰教练或有角色设定的冒险伙伴？

已明确的核心方向：独立看板、用户接取、前置隐藏、过期收回、完成才归档。其余默认建议：自动发布但不擅改手动事项；无惩罚性掉级；每日先发布少量可接任务，不强制接取；先一条主线；已有经济与数据保留。

衡量效果：是否更容易开始今天的一项行动、任务是否真的推进里程碑、用户是否频繁需要删掉/改小 AI 的任务。模型消息数量、任务数量和使用时长不作为主要成功指标。
